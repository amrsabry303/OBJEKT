**Consistency pass (17 Sept 2026, same day, second review):** a follow-up external review of the v3 PDF caught real residual defects the first pass missed — confirmed all of them independently before fixing. Root causes: (1) the first pass only edited launch-collection summaries/briefs/products, never touching `core_categories` rationale text or several `held_for_later`/`reason_if_defer_or_reject` fields, which still had regulatory/capacity-gating language; (2) two list-rebuild patterns in the script (`[filter] + [append]` on `required_outputs`) were NOT idempotent like the string-replace edits were, so re-running the whole script 5-6 times while incrementally adding checkpoints caused those list items to duplicate 5-7×; (3) a copy-paste error gave the register's Console row "~10 units" when the roadmap said 5 (10 was always the side-table figure); (4) the Furniture 5th piece was both a category inside `launch_collection` (implying launch) AND labelled "Later phase" in the register (implying a known gate) — neither was right since it's genuinely undecided, needed its own "Unresolved" status; (5) merging a design into an existing category by appending a whole NEW category object with the same name (instead of pushing into the existing category's `designs` array) silently created a duplicate "Tabletop" category, breaking the category count. **Lesson:** when a script will be re-run many times as edits accumulate, EVERY mutation must be idempotent, not just the ones that felt risky — `list = [x for x in list if ...] + [new_item]` duplicates on rerun; guard it with `if new_item not in list`. Also: after a big edit, re-derive summary/count fields programmatically from the actual data (`len(categories)`, not a hand-typed number) and assert they match, rather than hand-writing a count that can drift.
